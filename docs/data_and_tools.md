# 데이터와 도구

**최종 갱신**: 2026-08-06

데이터 형식, 보존 정책, 도구 사용법, 그리고 **분석 전 반드시 적용해야 하는
전처리**를 정리합니다.

## 1. 데이터 보존 정책 — 무엇을 지우면 안 되는가

### 결론부터

| 대상 | 용량 | 판정 |
|---|---|---|
| `output/*(No Fan)/*.csv`, `*(with Fan)/*.csv` | **110 MB** | **절대 삭제 금지 — 복구 불가** |
| `output/*/**.avi` (6월분) | 2.1 GB | 삭제 가능하나 실익 없음. 보관 권장 |
| `output/raw_output/` (파일럿 Y16) | 790 MB | 보관 — FFC 특성 규명의 원본 근거 |
| **합계** | **3.00 GB** | |

### 왜 CSV를 지우면 안 되는가

6월 CSV 82개(카메라당 41개, 총 416,000행)는 **2026-06-12~15 Fan/No-Fan 실험의
유일한 라디오메트릭 기록**입니다. SDK가 Y16 원본에서 계산한 실제 온도값이며,
같은 폴더의 AVI로는 **재생성할 수 없습니다** (AVI는 프레임별 auto-gain이 걸려
있어 온도 정보가 파괴되어 있습니다 — 2-3절 참조).

"with Fan 구역이 No Fan보다 일평균 0.4~0.7°C 낮다"는 실험 결과가 여기서 나왔습니다.
이 파일을 지우면 그 실험은 영구히 사라집니다.

### 왜 AVI도 굳이 지울 필요가 없는가

6월 AVI 82개는 2.1 GB입니다. 새 Y16 수집이 **하루에 8.1 GB**를 만들어내므로,
전체 `output/` 3 GB는 **새 데이터 반나절치도 안 됩니다.** 지워서 얻는 공간이
사실상 없습니다.

AVI의 잔존 가치는 제한적이지만 0은 아닙니다 — 6월 당시 생육 단계의 장면을 담은
유일한 시각 기록이고, 마스크 라벨링용 형태 정보로는 여전히 쓸 수 있습니다
(형태는 유효, 온도만 무효). 공간이 정말 부족하면 **하루 1개씩만 남기고**
(8개, 약 250 MB) 나머지를 지우는 정도를 권합니다.

### 앞으로 생성될 데이터의 보존

| 종류 | 보존 |
|---|---|
| `.y16raw` + `.y16meta` | **원본. 절대 삭제 금지.** 둘은 반드시 같은 폴더에 함께 |
| `.csv` | 보존. ROI를 안 그렸으면 내용이 비지만 타임스탬프 기록으로는 유효 |
| `.avi` | 참고용. 공간 부족 시 1순위 삭제 대상 |
| `.npy` / `.png` (파생물) | 삭제 가능. `.y16raw` 에서 언제든 재생성 |

## 2. 파일 형식

### 2-1. 녹화 1회(또는 분할 1개)당 4개 파일

```
raw_output/
├── 192_168_0_151_20260806_090000.y16raw    # uint16 LE 연속 프레임
├── 192_168_0_151_20260806_090000.y16meta   # JSON 메타데이터
├── 192_168_0_151_20260806_090000.csv       # ROI별 Min/Avg/Max 온도
└── 192_168_0_151_20260806_090000.avi       # 참고용 시각화
```

파일명은 `{IP를 _로 치환}_{YYYYMMDD}_{HHMMSS}` 이며, **네 파일이 같은 이름으로
함께 분할**되므로 `.csv` 의 N번째 행이 `.y16raw` 의 N번째 프레임에 정확히
대응합니다.

### 2-2. `.y16raw`

헤더 없는 연속 바이너리. `uint16` little-endian.

```python
import numpy as np, json
meta = json.load(open("....y16meta", encoding="utf-8"))
arr = np.fromfile("....y16raw", dtype="<u2").reshape(
          -1, meta["height"], meta["width"])          # (frames, 120, 160)
```

### 2-3. `.y16meta` (JSON)

| 키 | 내용 |
|---|---|
| `width`, `height`, `frame_count`, `fps` | 형상 |
| `timestamps[]` | 프레임별 촬영 시각. **프레임 수와 길이가 같음** |
| `raw_to_temperature_lut` | **raw→섭씨 변환표 (1024 포인트)**. 카메라·SDK 없이 복원 가능 |
| `rois[]` | 녹화 시점의 ROI 정의 (타입·좌표·근사 화소 수) |
| `camera_ip`, `camera_label`, `camera_format`, `temp_unit` | 카메라 정보 |
| `raw_value_min`, `raw_value_max` | 전체 프레임의 raw 최소·최대 |

**온도 복원**:

```python
lut = meta["raw_to_temperature_lut"]
xs  = np.arange(lut["count"]) * lut["stride"] + lut["raw_start"]
celsius = np.interp(arr.astype(float), xs, lut["values"])   # (frames, H, W) °C
```

### 2-4. `.csv`

```
timestamp,roi0_ellipse_params,roi0_ellipse_min,roi0_ellipse_avg,roi0_ellipse_max,...
2026-08-06 09:00:00.115,"(50,30 20x20)",18.50,19.20,19.80,...
```

ROI가 없으면 `timestamp,min_temp,avg_temp,max_temp` 헤더에 0.00이 기록됩니다.
**ROI 좌표는 원본 화소(160×120) 기준**입니다 — 6월 데이터는 720×480 기준이었으니
혼동하지 마십시오.

### 2-5. ⚠️ `.avi` 를 온도에 쓰지 마십시오

SDK가 만드는 AVI에는 **네 겹의 손실**이 있습니다.

| 손실 | 내용 |
|---|---|
| **프레임별 auto-gain** | 매 프레임 밝기를 0~241로 풀스케일 스트레치. 온도가 올라도 밝기는 그대로거나 내려감. 실측: .152에서 온도-밝기 상관 **r = −0.507** |
| 의사색 컬러맵 | INFERNO 계열 팔레트 → 그레이스케일 변환이 비선형 손실 |
| XVID 손실압축 | 색상당 약 13단위 오차. 순수 LUT면 256색이어야 할 프레임에 고유색 17,000개 이상 |
| 보간 업스케일 (구버전) | 160×120 → 720×480, 종횡비 4:3 → 3:2 왜곡 |

**AVI는 눈으로 확인하거나 마스크를 그릴 때만 쓰십시오.**

## 3. 도구 사용법

### 3-1. 녹화 — `multi_cameras_multi_roi_y16.py`

```bash
cd ubuntu_python_stream/
python3 multi_cameras_multi_roi_y16.py                  # 원본 160x120 (기본)
python3 multi_cameras_multi_roi_y16.py --no-avi         # Y16 + CSV 만
python3 multi_cameras_multi_roi_y16.py --output /data/thermal
python3 multi_cameras_multi_roi_y16.py --query-size 720x480   # 권장하지 않음
```

**예약 녹화 순서**
1. (선택) ROI 드래그 — 원본 화소 기준 크기가 표시되고 9화소 미만이면 경고
2. "예약 녹화 설정" 클릭 → 시작 0시 / 종료 24시 → "반복 간격" 체크 → 20분 / 3분
3. "예약 시작"

**주의**
- **녹화 중에는 ROI를 바꿀 수 없습니다.** CSV 열 수가 깨지는 것을 막기 위함입니다.
  ROI는 예약 시작 전에 그려두십시오.
- ROI를 안 그려도 Y16 원본은 정상 저장되며, 온도는 사후에 임의 영역으로 계산 가능합니다.
- 파일은 1시간 또는 1.4 GB마다 자동 분할되며 4개 파일이 함께 전환됩니다.

### 3-2. 판독 — `read_y16.py`

```bash
# 메타데이터·온도 통계
python3 read_y16.py info raw_output/

# 품질 진단 — 장기 운용 중 정기 실행 권장
python3 read_y16.py check raw_output/
python3 read_y16.py check raw_output/ --ffc-threshold 0.3 --hotspot-delta 2.0

# PNG 범위를 정하기 위한 온도 범위 조사
python3 read_y16.py range raw_output/

# 섭씨 float32 배열 (FFC 손상 프레임 자동 제외)
python3 read_y16.py npy raw_output/ --out temps/ --stride 10

# 라벨링용 8-bit PNG — 고정 온도 범위 필수
python3 read_y16.py png raw_output/ --out frames/ --tmin 17 --tmax 22 --stride 300
```

`check` 가 진단하는 것:

| 항목 | 내용 |
|---|---|
| 프레임 간격 | 타임스탬프 기준 끊긴 구간 |
| **셔터(FFC)** | 주기·계단 크기·일관성. 타임스탬프 공백과 온도 점프의 합집합으로 검출 |
| 불량 화소 | 고정 화소, 변동폭 이상 화소 |
| 극단값 위치 | 몇 번 프레임 어느 좌표인지, 상시인지 일시적인지 |
| **고정 물체** | 캐노피 중앙값 대비 ±2°C 이탈 영역 (일사센서·구조물 탐지) |
| 권장 PNG 범위 | 극단값을 잘라내고 캐노피 대비를 살리는 `--tmin/--tmax` |

> ⚠️ PNG 내보내기 시 `--tmin/--tmax` 를 **모든 파일에 동일하게** 지정하십시오.
> 프레임별 자동 정규화는 AVI와 같은 문제를 재현해 학습·라벨링 데이터를 망칩니다.
> 지정하지 않으면 스크립트가 거부합니다.
> 학습 입력은 `--colormap` 없이 회색조를 쓰십시오 — 컬러맵은 정보를 늘리지 않고
> 채널만 3배로 늘립니다.

## 4. ★ 분석 전 반드시 적용할 전처리 5단계

실측으로 확정된 것입니다. 하나라도 빠뜨리면 결과가 왜곡됩니다.

```python
import numpy as np, cv2, json, sys
sys.path.insert(0, "ubuntu_python_stream")
from read_y16 import (load_meta, load_raw, temperature_converter,
                      frame_mean_celsius, detect_ffc, bad_frame_mask)

meta = load_meta(path); arr = load_raw(path, meta)
conv = temperature_converter(meta)

# ① FFC 직후 손상 프레임 제외 (상단 행이 깨져 −17°C, +46°C 등이 섞임)
tmean = frame_mean_celsius(arr, conv)
keep  = bad_frame_mask(arr.shape[0], detect_ffc(tmean, meta), skip=3)
idx   = np.where(keep)[0]

# ② 프레임별 전역 평균 제거 — FFC 톱니 제거 (시간 std 71% 감소)
blk = conv(np.asarray(arr[idx])).astype(np.float64)
det = blk - blk.mean(axis=(1, 2), keepdims=True)

# ③ 저주파 배경 제거 — 개체 구조 부각 (구조 스케일 49 → 24화소)
img = det.mean(axis=0).astype(np.float32)
hp  = img - cv2.GaussianBlur(img, (0, 0), 12)

# ④ 분석 영역 한정 — 하단 15행은 선반 구조물
hp = hp[:105, :]

# ⑤ .152 는 일사센서 영역 제외
mask = np.ones_like(hp, bool)
if "0_152" in path:
    mask[31:36, 102:109] = False
```

### 각 단계의 근거

| 단계 | 근거 |
|---|---|
| ① | FFC 재개 직후 1~2 프레임의 y=0,1 행이 손상. 물리적으로 불가능한 값 발생 |
| ② | 시간 표준편차가 톱니에 지배당함: 0.324 → 0.094°C. 남은 값은 NETD의 2배로 실제 장면 변동 |
| ③ | 원본은 비네팅·구조물의 큰 스케일 그래디언트가 지배. 6월 AVI에서 구조가 잘 보였던 건 auto-gain이 고역통과 필터로 작동했기 때문 |
| ④ | y≥105 가 두 카메라 공통 구조물 띠 (최대 +3.4°C) |
| ⑤ | .152 의 x 102~108, y 31~35 (17화소, +1.81°C) |

> **Otsu를 쓰지 마십시오.** 온도 히스토그램이 이봉이 아니라 **단봉 + 따뜻한 꼬리**
> 임을 실측으로 확인했습니다(평균−최빈 +0.29~0.35°C). Otsu의 전제가 깨집니다.
> 대안은 [기획서 5-2 Tier 0](leaf_segmentation_plan.md)의 Deery M2 방식.

## 7. 알려진 함정

| 함정 | 내용 |
|---|---|
| **두 카메라를 프레임 번호로 맞추기** | 독립 클럭 + FFC 횟수 차이로 어긋납니다. 반드시 `.y16meta` 의 `timestamps` 로 정렬 |
| **`.y16meta` 를 잃어버리기** | LUT가 없으면 온도 복원 불가. `.y16raw` 와 항상 같은 폴더에 |
| **프레임별 자동 정규화 PNG** | AVI와 같은 문제 재현. 고정 범위 필수 |
| **6월 ROI 좌표를 그대로 쓰기** | 6월은 720×480 기준, 현재는 160×120 기준 |
| **720×480으로 녹화** | 보간이라 정보 증가 없이 용량 18배 |
| **초해상도 후 온도 계산** | hallucination된 화소가 곧 온도값이 됨 |
| **구버전 `multi_cameras_multi_roi.py` 사용** | AVI만 저장 + ROI 온도 경쟁 상태 버그 |
| **팬 구역(.152)을 같은 기준으로 평가** | 열 대비가 No Fan의 절반. 모델 평가를 구역별로 분리할 것 |
